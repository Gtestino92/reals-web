## Permanent migration methodology

1. Read the complete Android entry point and trace delegated composables, modifiers, coordinators, callbacks, domain presentation helpers, lifecycle owners and resource cleanup. Record reference revision and screenshots.
2. Inventory all visible states and transitions, gestures, animation, accessibility, pending/failure paths, navigation and tests. Include behavior hidden behind conditions.
3. Compare actual Web behavior, source and tests. A matching endpoint or button is insufficient. Keep separate visual, interaction and lifecycle findings.
4. Implement Android behavior by default. Adapt density, viewport, keyboard, pointer and browser media capabilities only with an explicit reason. Backend contracts remain authoritative if Android locally predicts a business transition.
5. Test the corresponding behavior, including cancellation, obsolete work, negative cases and real browser event arbitration. Distinguish jsdom, browser emulation and physical devices.
6. Update this matrix and document justified differences and outstanding work before delivery. New migrations must repeat the process rather than inherit an assumption of completeness.

Status: **COMPLETE** means the narrowly described behavior is implemented and covered; **PARTIAL** means differences remain; **MISSING** means absent; **PLATFORM-LIMITED** means browser capability constrains parity. Rows describing a whole flow remain PARTIAL when any material state or visual treatment differs.

Android source paths below are relative to `../reals-app/app/src/main/java/com/reals/app/`. Android test names refer to `app/src/test/java/com/reals/app/`; Web tests are in `src/`. Shared sources can contain Second Chat behavior; that behavior is explicitly outside this migration.

## Mutation and resource review for this implementation

| Path | Invariant / response installation |
| --- | --- |
| Pointer down/move/up | One pointer owner, horizontal lock after slop, raw distance capped at 150; select only at release >=60. Clear ownership before invoking callback; duplicate release cannot select again. No deferred reply callback. |
| Vertical/left/tap/cancel/lost capture | No reply, reset transform. `touch-action:pan-y pinch-zoom` leaves vertical scrolling to browser. Interactive children and Shift-drag mouse selection are excluded; ordinary text is a valid swipe target. |
| Eligibility/question/identity/unmount | Disable cancels gesture, question instance key remounts target, message identity keys stable; capture is acquired on down, child capture-loss events are ignored, and the captured element is released using its owner reference even after ref detaches. Native capture handles release outside target. No global listeners or gesture timers. |
| Reply installation/clear/send | Existing `beginReply` selects immutable ID and direct preview and focuses composer only after intentional action. Submission validation/confirmation and uncertain-send safeguards unchanged. |
| Heart click/pending/completion | Ref synchronously rejects duplicate clicks; pending controls disabled, confirmed response alone fills heart. Existing ChatSession write lock, errors, canonical merge, reload, serial and lifetime cancellation remain authoritative. No new API or optimistic reaction truth. |
| Unmount during heart request | Local generation rejects obsolete pending-state completion; session owns request cancellation and response rejection. No unmounted component installs response state. |
| Reaction/reply geometry | Fixed 48px lane and reserved outgoing badge space; reaction metadata never sets scrollTop; only reply-composer changes preserve bottom when previously near bottom. No new-message indication or focus from a reaction update. |

## Focused correction: reaction geometry and realistic swipe starts

Web base `6d0d4a1`, initially clean. Re-read Android `ChatChrome.replySwipeTarget`, reaction/scroll helpers, `FirstChatPanels`, `ChatReplyPresentation`, corresponding reply/scroll unit tests and backend HEART/reply contracts. No unrelated parity gap was implemented.

Confirmed causes reproduced in isolated Chrome fixtures before application edits:

- The global busy status entered normal flow during HEART writes. At 390px the timeline moved down 30px and shrank from 422 to 392px; at 1440px it moved 32px and shrank from 492 to 460px. Errors in normal flow added further displacement (130px mobile / 84px desktop relative to baseline).
- The metadata-dependent layout effect forced a reader 30px from the bottom to the absolute bottom after success. Bubble dimensions themselves stayed constant; their anchoring/available viewport changed.
- The mouse text-element exclusion rejected legitimate starts. Late capture also missed a quick move outside a short bubble. Touch implicitly captured the text child; its bubbling `lostpointercapture` during transfer reset the wrapper's active gesture. Pointer traces distinguish this from a genuine `pointercancel`.
- Reply selection used only the last move's distance. A release at 90px after the last delivered move at 18px failed. Browser event coalescing on physical devices remains a possible trigger, not a verified device-specific cause.
