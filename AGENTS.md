# Reals Web engineering instructions

- Inspect current files and relevant tests first. Verify branch, HEAD and working-tree changes before edits; compare with the task base when available. On an unborn repository, report that no HEAD/base comparison exists.
- Use the explicitly requested task branch. Otherwise branch from the latest available `development` using a scoped prefix (`feature/`, `fix/`, `docs/`, etc.) and `--no-track`. Never implement on `development`, `main` or `master`, or track a protected base from a work branch.
- Configure `git config --local push.autoSetupRemote true` so the first explicitly authorized plain `git push` automatically establishes the upstream to the same-named remote work branch. Keep `--no-track` when branching from a protected base; never set the work branch upstream to `origin/main`, `origin/master` or `origin/development`. This configuration does not authorize a push.
- Keep changes scoped; avoid unrelated refactoring, visual redesigns, contract changes and speculative abstractions. Treat sibling repositories as read-only unless explicitly authorized otherwise.
- Use React function components, strict TypeScript and plain CSS tokens. Keep rendering presentational; introduce hooks or API modules only when behavior needs them. Avoid `any`, unchecked casts, unnecessary dependencies and global state infrastructure.
- Backend contracts and lifecycle state are authoritative. Consult `../reals-backend/docs/commons/` before integration. Timers are advisory; do not infer expiry, penalties, moderation or eligibility as domain truth. Refresh authoritative state after meaningful actions.
- Before stateful/async changes, identify invariants and all mutation/response-installation paths in a compact review matrix. Update coupled fields atomically. Review stale closures, overlapping requests, out-of-order responses, retries/idempotency, missing/malformed fields, background/resume and sign-out races. Cancel effects/listeners/timers and reject obsolete responses; cleanup must respect resource ownership, not invent business transitions.
- Handle failures explicitly, including non-success HTTP responses. Provide safe actionable errors; distinguish terminal session invalidity from transient failures. Do not silently swallow failures or blindly retry mutations.
- Render user/backend text as React text. Do not introduce raw HTML rendering without an explicit security design. Never commit credentials, service accounts or tokens; never log passwords, tokens, personal text, full emails, private media URLs or sensitive payloads. All `VITE_*` values are public client data.
- Read/write text explicitly as UTF-8; preserve Spanish accents, ñ, ü, ¿ and ¡. Inspect new/changed strings and scan for mojibake before delivery. Do not rewrite unrelated encoding, formatting or line endings.
- Use Vitest and React Testing Library for focused behavior tests and regressions. Cover materially distinct mutation paths when changing state; prefer accessible role queries and fake dependencies. During iteration, run only the smallest relevant focused tests (`npm run test:focused -- <test paths>`), with compact output; run typecheck after meaningful TypeScript changes. Run the complete suite once at final validation, repeating only for failures or subsequent material changes. Run build before delivery and Chromium scenarios relevant to changed browser behavior. Keep the full CI regression suite. Report exact commands/results and untested limitations; see `docs/testing.md` for selection guidance.
- Keep workflow rules here, frontend documentation in `docs/`, and backend contracts in their owning repository. Link references rather than duplicating large documents or deferred Android backlogs.
- Do not commit, push, merge, create/close PRs, deploy or change deployment resources without explicit authorization. Before delivery review the diff and report changed files, decisions, validation, risks and next steps. Include invariants/mutation review for stateful changes and a diff summary.

## Android-first feature migration and parity requirements

Reals Web must be a near-exact functional and visual clone of Reals Android, adapted only where browser/platform differences justify it. These requirements apply before implementing or modifying any user-facing feature.

- **Inspect the complete Android flow first.** Android in `../reals-app` is the canonical product reference. Trace the relevant Composables, ViewModels, coordinators, navigation, models, state policies and helpers, including delegated functionality outside the main screen. Inspect existing unit and instrumentation tests, screenshots, assets and documentation. Screenshots supplement source inspection; do not infer missing behavior from screenshots alone. Use the [Android reference and source map](docs/android-reference.md) as an entry point, then inspect the current source.
- **Audit before implementation.** Compare Android with the current Web implementation in a concise parity analysis: visual structure/styling; interactions, gestures and animations; navigation/system Back; state transitions/lifecycle; loading, disabled and empty states; errors/recovery; timers, polling and background/resume; keyboard, focus, accessibility and scrolling; mobile/desktop behavior; and backend interactions. Classify each relevant behavior as `COMPLETE`, `PARTIAL`, `MISSING` or `PLATFORM-LIMITED`. An endpoint or button alone does not establish completeness.
- **Implement parity within the authorized scope.** Reproduce Android behavior by default, preserving secondary actions, gestures, confirmation dialogs and unusual states instead of substituting simplified controls. Do not invent business rules. Reuse the Web architecture where appropriate, adapt desktop layouts responsively while preserving Android's mobile experience, and support touch, pointer, mouse and keyboard accessibility. When faithful browser reproduction is impossible, document the limitation and implement the closest justified alternative.
- **Respect both owners and repository boundaries.** Android defines the user experience; the backend defines authoritative API contracts and domain state. `reals-app` and `reals-backend` are read-only without explicit developer authorization. Do not change backend contracts, lifecycle policies, schedulers or persistence to compensate for missing Web functionality. Report independently discovered backend defects separately; do not fix them as part of a Web task.
- **Maintain one parity matrix.** Reuse [docs/android-parity-matrix.md](docs/android-parity-matrix.md), preserving ongoing work. Update the relevant sections with feature/Android source references, expected behavior, Web implementation locations, parity status, validation evidence and outstanding differences. Keep entries concise; link source documentation instead of copying it or creating duplicate parity documents. Never describe untested behavior as verified.
- **Validate parity, not just compilation.** For every feature, add focused behavioral and regression tests covering relevant gestures, navigation, edge cases and state changes. Compare important UI states against Android screenshots and source; validate mobile and desktop layouts. Distinguish simulated browser tests from real-device testing and report unsupported, incomplete or unverified behavior. Passing typecheck, unit tests and build alone does not establish Android parity.
- **Report discrepancies proactively.** At delivery, state what Android functionality was audited, what was implemented, what is functionally equivalent, what remains partial or missing, justified browser differences, tests performed and remaining validation. Identify relevant omissions without waiting for the developer to find them. An audit does not authorize unrelated implementation or scope expansion; report larger or unrelated gaps for later prioritization.
